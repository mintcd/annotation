# Change Synced Data

Use this guide when adding a synced table or changing synced columns.

## Files Involved

- [migrations/](../../migrations)
- [sync.next.config.ts](../../sync.next.config.ts)
- [app/sync/sync.generated.ts](../../app/sync/sync.generated.ts)
- [core/persistence/syncData.ts](../../core/persistence/syncData.ts)
- [@types/database.d.ts](../../@types/database.d.ts)
- tests under [tests/](../../tests)

## Normal Workflow

1. Add a D1 migration.
2. Apply the migration to the intended database.
3. Make sure `sync.next.config.ts` includes the table if it should sync.
4. Run:

   ```sh
   npm run sync
   ```

5. Update app-level types in `@types/database.d.ts` if needed.
6. Add or update helpers in `core/persistence/syncData.ts`.
7. Update UI code to use helpers instead of touching sync tables directly.
8. Run checks.

## Generated Files

Do not hand-edit:

- `app/sync/sync.generated.ts`
- `public/sw.sync.js`

They are generated by `npm run sync`.

## Flush Modes

`syncData.ts` uses three write flush modes:

- `background`: queue a sync and do not block the UI
- `await`: wait for sync before resolving
- `none`: write locally without syncing yet

Use `await` only when the next user action depends on the server seeing the row.
For example, route navigation needs `ensureWebsiteAvailableForRoute()` because
the server page resolves website IDs from the remote sync stream.

## Current Migration Caution

The generated sync schema currently includes columns/tables that are not fully
represented by the checked-in migrations:

- `annotations.exact`
- `annotations.prefix`
- `annotations.suffix`
- `page_notes`

Before recreating a fresh D1 database from migrations, add migrations for those
schema pieces or recover the missing migration history.
